# Tier 2 Checkpoint

Living document. Update this whenever a prompt lands or the scope changes — it should always answer "what's built, what's verified, what's left" without needing to reread the whole conversation history.

This repo covers **Tier 2 only** (structural drug-response prediction). Tier 1 (evidence retrieval) is a separate scope owned elsewhere — see `docs/tier 1 docs/` for the one Tier-2-independent doc that used to live alongside these; the remaining docs (`architecture.md`, `api-contracts.md`, `data-sources.md`, `ui-flow.md`, `validation-plan.md`, `tech-stack-setup.md`) describe both tiers and stay put since Tier 2's own sections in them are load-bearing.

## Workflow convention

Each pipeline step is scoped as a numbered Cursor prompt in `docs/tier2-verification.md`, built one at a time. After each prompt lands, it gets reviewed here in this session before the next prompt is written: code read in full, tests rerun independently (not just trusted from the report), edge cases probed by hand, live integration claims re-verified from scratch where practical. Bugs found in review get fixed in the same pass, with a regression test added. Commits are written by this session as ready-to-run heredoc commands but executed by the user (their rule, not renegotiable).

## What's built and verified

All five modules below are independently unit-tested, have live-integration tests against the real external services, and were re-verified by hand in review (not just taken on the report's word). All follow the same failure-handling contract: every external call has a dedicated exception type, caught at the specific call site, never a bare `except`/`Exception`, and falls through to the next source or an explicit "unavailable" result rather than crashing.

## What's left (in scope for this repo)

Ordered roughly by what blocks a working end-to-end demo first.

1. **Step 6 — Threshold labeling.** Not built yet. `tier2-structural-prediction.md` §Step 6 requires converting each candidate's `delta_score` into one of three labels (`likely_reduced_binding` / `likely_retained_or_increased_binding` / `uncertain`) using an empirically-chosen cutoff, explicitly documented as an internal heuristic, not a validated clinical threshold — both in code and in the UI disclaimer. This cutoff has to be chosen using `validation-plan.md`'s gold-standard cases (see #3 below), so it can't be picked arbitrarily.

2. **Step 7 — Output assembly.** Not built yet. Currently the five modules (mutation validation → AlphaMissense → structure → candidates → binding score) exist as independently-callable functions, not a single pipeline. Need one function that: runs them in order for a given mutation, loops Steps 5–6 over every candidate from Step 4, and assembles the result into the exact `api-contracts.md` "Tier 2 result item" schema — including the fixed §10 disclaimer text attached to every item from a single shared constant (not re-typed per call site, per that doc's explicit rule).

3. **Run `validation-plan.md`'s gold-standard cases.** Not done. Nine cases (EGFR T790M, ABL1 T315I, BRAF V600E, etc.) need to run through the assembled pipeline once Step 7 exists, checking resistance-vs-sensitive directionality. Pass threshold and the two hard-required positive controls (BRAF V600E/vemurafenib, EGFR T790M/osimertinib) are pre-committed in that doc — do not adjust the criteria after seeing results. This also determines the Step 6 label cutoff and whether the binding-affinity delta/label can be shown at all, or whether the pipeline has to fall back to the narrower "binding pocket proximity + AlphaMissense only" claim per that doc's own fallback clause.

4. **Demo-case caching.** Not done. `tech-stack-setup.md` step 8 and `architecture.md`'s deployment notes both require pre-computing and caching the 2 locked demo cases' full pipeline output so the live demo never depends on external API latency/uptime — especially load-bearing for mCSM-lig (synchronous but not documented-fast) and Vina (real compute time).

5. **AutoDock Vina fallback coverage gap.** Not a bug, but worth tracking: per Prompt E's own finding, most PubChem/DGIdb candidates won't have a PDB HET code, so Vina — not mCSM-lig — carries most of the real traffic despite being the "fallback." Its accuracy characteristics (no published correlation figure the way mCSM-lig has ρ up to 0.67) should be represented honestly in whatever labeling/confidence framing Step 6 produces, and `validation-plan.md`'s "cite real accuracy figures, not assumed ones" rule applies here too.

6. **Out of scope for this repo, tracked elsewhere:** CTRI access-mode verification (Tier 1), the FastAPI orchestration layer that decides Tier 1 vs. Tier 2 routing (`architecture.md`'s "Orchestration backend" — spans both tiers, likely owned alongside Tier 1), the frontend, and the LLM synthesis layer's citation-enforcement check.
